Fixed (hook processes on adapter paths): gates launched by one adapter event now share one timeout watchdog instead of starting one each. This applies to adapters that start `hook-gate.sh` once per registry hook, such as bot runtime adapters that set `HQ_HARNESS=codex`; the Codex and Grok adapters in this repo run registry hooks in-process and reach `hook-gate.sh` only through `hqad_launch_registered_hook`'s fallback. An adapter that sources `core/scripts/lib/hook-adapter-core.sh` with `HQ_HARNESS` set to `codex` or `grok` exports `HQAD_DISPATCHER_PID`. A gate whose parent is that live process arms one `hook-timeout-watchdog.sh` for the event and records it in `workspace/.hook-timeout-sentry/gate-event-<pid>.pid`; later gates arm nothing while it is alive. Each gate writes its hook, pid and start time to `<claim>.active`, and the shared watchdog warns about the gate that runs to its own warning point, as a per-gate watchdog did (at most about 4 s later). Like a per-gate watchdog, which reads payload metadata and configuration only after its gate outlives a 1 s grace, it does that work only once the same gate is still running at two checks 1 s apart, so an event of fast gates costs it a date and a few sleeps. It warns only about a gate at least 2 s old, checks at most 4 s apart and exits within about 4 s of the adapter. Known limits: an adapter that runs gates in parallel from one shell gets only the last-started gate timed; a gate under a Bash without `EPOCHSECONDS` is dated from its active entry's mtime (one stat when first seen); the active entry can outlive an event whose last gate was the one reported. Any other gate, or one without a writable claim, keeps its own watchdog as before. The watchdog only reports, so no hook output, exit status or decision changes, and the hard bounds (adapter caps, master-hook guard caps, the runtime's hook timeout) are unchanged. Covered by `core/scripts/tests/hook-gate-event-watchdog.test.sh`.
