Changed (`hq-never-ask-user-to-run-commands`, v1 to v2): added a third exception for steps only the person can do, when the step is needed for a task the person asked for and there is nothing to click instead: an interactive password or `sudo` prompt, a license acceptance, an OAuth sign-in that only the host lets the person start, or a step a host safety classifier refuses to the assistant that the person explicitly asked for in this session. Under it the assistant says briefly why it cannot do the step and gives the one command. For any other irreversible step it announces per `hq-announce-before-irreversible`, gives the command, and does not run the step itself after a yes. The new exception never covers a step the person declined, one an HQ hook or scan blocked, one that crosses a company boundary, or one that deletes data, force-pushes, skips hooks, widens the assistant's own permissions or turns off a guard; deliberate HQ safety blocks are still handled by the existing exception for them. It also never covers production deploys, messages or posts, database migrations, DNS changes, billing changes or API calls that create records that cannot be deleted: for those the assistant asks the person to confirm, tries the same step once more, unchanged, after a yes, and stops and reports if the step is still refused. The command never contains a password, one-time code or secret value, and the assistant never asks for one. Change from v1: v1 named `/mcp` as an example of a command never to give. The rule line no longer names it, and a host-only OAuth start such as `/mcp` now falls under the new exception.
