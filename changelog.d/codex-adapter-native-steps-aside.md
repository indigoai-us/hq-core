Fixed (hooks, Codex): inside an HQ root, Codex runs two hooks for any event that `hq reindex` has switched to the native engine (core.next): the engine's entry in the user-scope hooks.json, and this adapter from the tracked `.codex/config.toml`. It runs both at once. Both used to run the whole event, and their policy injectors shared one session ledger, so the model got two partial sets of reminders and every other hook of the event ran twice. The engine (hq-cli, `host::answered`) now marks each Codex event it answers just before its answer goes out. The mark is a file in `${HQ_HOOK_STATE_DIR:-~/.hq/state/hq-hook}/codex-answered/` keyed by the HQ root's real path, the payload's session id, the event and a digest of the exact payload, so an answer for one HQ root never makes another root's adapter stand aside. `.codex/hooks/hq-codex-hook-adapter.sh` stands aside (exit 0, no output) only when the mark with its own key appears within `HQ_CODEX_NATIVE_WAIT_MS` (default 4000, at most 10000, so the wait and the shell answer always end at least 1 s inside the 30 s Codex timeout; SessionEnd, with a 3 s timeout, waits at most 300 ms. The wait is timed by the clock through perl; without perl the adapter looks once and does not wait) and was written in the last 10 seconds. It then consumes the mark. No hooks.json is read. An engine that is not registered, not trusted, turned off in Codex, crashed or gave no verdict writes no mark, so the adapter answers as before. The wait runs only for an event the engine has answered on this account in the last week (its `event-<Event>` hint), so events left on the shell and machines without the engine pay nothing. The adapter also answers as before, with no wait, when it was started with the event argument (the engine's kill-switch hand-back), when a kill switch is set (`HQ_CORE_NEXT` or `HQ_HOOK_ENGINE` off, `~/.hq/state/core-next.off`, `~/.hq/hook-engine.off`), on Windows, and with `HQ_CODEX_NATIVE_STEP_ASIDE=0`. Test: `core/scripts/tests/codex-adapter-native-steps-aside.test.sh`, added to the hook-registration workflow.
