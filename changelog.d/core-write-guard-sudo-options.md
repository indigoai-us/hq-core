Fixed (security, core-write guard): a write behind `sudo` with options was not checked. The command-name lookup skipped the word `sudo` and then took sudo's first option as the command, so `sudo -u nobody cp evil.sh .claude/hooks/x.sh`, `sudo -E cp ...`, `sudo -n -u root cp ...`, `sudo -- cp ...` and the same inside `$(...)` were allowed (only a bare `sudo cp ...` was blocked). `hq_shell_record_executable` in `core/scripts/hook-lib.sh` now skips sudo's options and their values (`-a`/`-c`/`-u`/`-g`/`-C`/`-p`/`-r`/`-t`/`-U`/`-D`/`-R`/`-T` take one, attached or in the next word; `-h` takes only an attached value, so a bare `-h` never consumes the command; combined short flags; `--user root` and `--user=root`; `--` ends them), which covers the guards that use it. Ordinary commands without sudo resolve exactly as before. `block-core-writes-bash.sh` is frozen and keeps its own lookup, so `hq_strip_tokens_containing_literals`, whose output that guard parses, now turns the options of a `sudo` in command position into `HQ_SUDO_OPTION=1` words, which the guard's lookup already skips; every other word keeps its place, and a command whose sudo option or option value has a quote, an expansion or an escape is left as written and judged as on main (`sudo -u "build user" cp ...` is not checked): the rewrite does not track quotes, so it replaces only plain words and never changes the quotes or operators of a command. `-D`/`--chdir` and `-R`/`--chroot` get the same `HQ_SUDO_OPTION=1` words and nothing else: they change only the sudo child's directory, never the caller's, so no `cd` is modelled for them. Earlier versions of this fix put `cd DIR; ` in front of the sudo, which changed the guard's cd tracking for the rest of the command: an outside DIR (`sudo -D /tmp true; cp evil.sh .claude/hooks/x.sh`) turned off the relative-path checks, and a relative DIR cleared a protected cwd from an earlier `cd` (`cd .claude/hooks; sudo -D sub true; cp evil x.sh`). Both shapes are blocked, as on main. A relative target after `sudo -D DIR` is checked against the caller's directory, so `sudo -D .claude/hooks cp evil x.sh` is allowed, as on main. `block-hq-root-git-mutation.sh` reads the `-D`/`--chdir` directory (`HQ_SHELL_SUDO_CHDIR`, set by `hq_shell_record_executable`) as a `git -C` anchor, so `sudo -D /tmp/other-repo git commit` is judged against that repository instead of the HQ root, and `sudo -D . git commit` at the HQ root is blocked like `git commit`. An unquoted newline ends the sudo command, so an option that takes a value at the end of a line (`sudo -u`, a newline, then `cp evil.sh .claude/hooks/x.sh`) does not take the next line's command as its value; that shape is blocked, as on main. Still open, not from sudo: the shared lexer does not split backtick substitutions, so `` echo `cp evil.sh .claude/hooks/x.sh` `` is allowed with or without sudo. Regression test: `core/scripts/tests/block-core-writes-bash-sudo-options.test.sh` (own CI step; not replayed by the parity harness).
